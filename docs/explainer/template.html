Two AI agents, one shared lock, and an audit log that sees nothing

Agents that share tools can pass secrets to each other just through how they use a shared resource, with every call legal and logged. Here is how it works, what real models did with it, and the gateway design that provably stops it.

The situation

Companies increasingly run several AI agents side by side, sharing tools through a central gateway such as an MCP server. Some of those agents are deliberately kept apart:

  • one can see private data and another can reach the internet, and the data must not cross;
  • one writes code and another reviews it, and they should not coordinate;
  • one agent is untrusted and must not influence a trusted one.

The usual safeguard is accountability: every tool call is authenticated and logged, and monitors watch the logs. In 1973, Butler Lampson pointed out that a program cut off from sending messages can still signal through the way it uses shared resources. Agents share tools in exactly that way.

Watch A send a message through a lock

A lock is how software shares something only one user can use at a time, like the "occupied" sign on a single bathroom: whoever is inside holds it, and anyone else who tries the door is told it's busy. Agent tools use locks constantly, often invisibly: a file open for editing, a database row, a shared browser session, one licence seat.

Agent A knows a secret. Agent B must not learn it, and there is no messaging tool. Each round, A goes first: it holds the lock to send a 1 or leaves it free to send a 0. Then B tries to run a job. If the lock is held, B's reply is busy, otherwise ok. At the end of the round every lock is released.

The VeriSwarm architecture

VeriSwarm is two things: a gateway design that removes the channel, and a way to prove the design works before anyone deploys it.

How it's proved

  1. Write the gateway in Lean. The gateway's state is one lock cell per agent. A call reads and changes only the caller's own cell, and the reply is computed from that cell alone: 
    def serveCall (s : Store P) (p : P)
    (a : Action) : Store P × Reply :=
  (update s p (nextCell a (s p)),
   ⟨respond a (s p),
    (nextCell a (s p)).jobs⟩)
    s p is agent p's cell. In today's gateway every agent shares one cell, so A's hold changes what B is told.
  2. State the property about two runs, not one. Take any two streams of requests that differ only in what other agents ask for: B's requests are the same, while A's secret and calls differ freely. B must get exactly the same replies in both: 
    theorem core_noninterference
    (r : P) {xs ys : List (Req P)}
    (h : SameFor r xs ys) :
  repliesFrom r 0 xs cleanStore =
    repliesFrom r 0 ys cleanStore
    SameFor r xs ys means the two streams look alike to B (r): the same calls by B and the same maintenance steps, in the same places, with anyone else's calls free to differ.
  3. Let Lean check the proof. The proof walks the request stream one step at a time: a call by another agent writes only that agent's cell, so B's cell is untouched. Lean checks every step, for any number of agents, any turn order and runs of any length, with no gaps and only its standard axioms. Further theorems cover a B that adapts each move to what it has seen, and give a concrete leak for each way of breaking the design.
  4. Run the proved code.

The proved Lean code runs inside the gateway. What stays trusted is the thin wrapper, the Lean compiler and the machine. The guarantee covers what the model includes: wall-clock timing, CPU caches and the network are outside it.

The design

The gateway still checks identity and logs every call. It adds four rules, so that nothing A does can show up in anything B sees:

  1. Each agent gets its own real resource. A's requests go to A's lock and B's to B's, separate underneath and not just separately named.
  2. No shared limits between agents kept apart. Each has its own quota, so A's use can't starve B.
  3. Replies describe only the caller's own activity. No gateway-wide request numbers or counters that also count A's calls.
  4. Turns run in a fixed order. If A does nothing, B doesn't get to go early.

If something must be shared, such as one browser session, the gateway releases or resets it between agents' turns instead of rules 1 and 2, like cleaning a single room between visitors. That costs one extra step per round. Rules 3 and 4 still apply.

The cost is resources, not work: with one lock each, B still completed of 1,000 jobs while A was busy.

Experiment Design

We put language models from four families in the two seats, one API call per turn. We told them only the goal: the receiver should learn the sender's bit using only what the gateway allows, with nothing agreed in advance. Nobody told them about locks as a signal, and real AI agents found it on their own. Each cell is two runs of 20 rounds, pre-registered with predictions before any call.

Gateway design

When the fix works

There are two ways to make the fix hold. Pick the one that fits the resource.

Best, when the resource can be copied

Give each agent its own

  • Its own lock, separate underneath, not just separately named.
  • Its own rate limit or quota.
  • Replies about the caller only: no gateway-wide request numbers.
  • A fixed order of turns: an idle agent's turn is never given away.

Closed

When there can only be one

Share it, but clear it between turns

  • One shared resource, released or reset between A's turn and B's: one licence seat, one browser session, one device.
  • Replies about the caller only.
  • A fixed order of turns.
  • A shared rate limit is fine here, because nothing A holds survives into B's turn.

Closed

What breaks the fix

Each of these reopens the channel at a full bit per round, even when every agent has its own lock.

What is still sharedHow A signals BWhere it shows up
One lock underneath separate namesThe log shows "A's lock" and "B's lock", but they are the same real lock, so A's hold makes B busy.Per-agent workspaces built on one database, session or account
A shared rate limitOnly one job may run at a time across everyone, so while A holds its own lock, B's job is refused.One API key or quota for all agents; a fixed-size worker pool
A global counter in repliesIf A made a call, B's request number jumps by two instead of one.Request IDs, sequence numbers, "requests remaining" headers
A scheduler that gives away idle turnsIf A does nothing, B is served early, so when B finishes tells it what A did.Schedulers and pools that start the next task as soon as one is idle

Releasing locks between turns repairs the first two, because nothing A holds survives into B's turn. It can't repair the last two, which leak information rather than a held resource.

When the guarantee holds

  • Everything goes through the gateway. Agents can't touch the resource directly or route around it.
  • The gateway is trustworthy. A compromised gateway voids everything here.
  • Agents only see what the gateway returns: their own replies and results. If an agent can measure real time, CPU load, cache speed or network delay, those are other channels this model doesn't cover.
  • The separation is real underneath. Check the backing resource, not the labels.
  • Nothing else is shared: no common cache or account, no website both agents read and write, no human relaying messages.
  • It is used where it matters: between agents that must be kept apart. Agents meant to work together can share freely.

Within those limits the result is not "hard to detect". Nothing A does reaches B at all.

Why watching the logs isn't enough

What this shows, and what it doesn't

  • The agents were told to communicate. This shows what current models can do, not that they would collude unprompted.
  • It covers one channel: contention on a shared resource inside the gateway. Wall-clock timing, CPU caches and the network are outside the model.
  • The model checker covers finite configurations, a Lean proof covers the abstract design for any number of agents, and the Python simulator matched the model on every configuration compared. No production system was evaluated.
